# TA Content Studio — agent guidance

## Product and source of truth
- This is **one** local, file-first Content Studio and **one** TA public website. The canonical authoring data is JSON, currently `content/site.json`; media are real files in `assets/`. **Do not add a second CMS, parallel Markdown content, or another demo site.**
- **Core flow:** JSON + assets → shared Card/Item renderer → `npm run build` → `dist/`. `npm run preview` serves the built website at http://127.0.0.1:4173/; `npm run package:site` optionally produces `release/website.zip` for transfer to another static host. Local authoring: `npm run dev` at http://127.0.0.1:5173/.
- Use the current `docs/IMPLEMENTATION_PLAN.md` as the **single living roadmap**, `docs/POST_V1_ARCHITECTURE.md` as the V2 architecture, and `docs/logs/` as dated historical records. Read the current roadmap and check the actual branch before working.
- Preserve recursive Cards (grid/layout/padding/gaps/rounding), atomic Items (text, image, button, rich content, dividers), editable records, references/queries, shared preview/public rendering, stable IDs/slugs and typed file-backed authoring. **M12:** Work and Journal now reference the same `page-general` one-main-slot Template, but own independent root `composition` Cards. In Studio, Page Design edits only the composition; Preview assembles template + content. Existing Home/Studio remain legacy until explicit reviewed conversion. **Shared semantic chrome:** `site.chrome` chooses default Navbar/Footer Component roots, optional `template.chrome` overrides them, and the component's single Card root is the actual `<nav>` or `<footer>` landmark. `site.navigation` is the sole source of link data; maintain draft filtering, active section, accessibility and direct link Items. Studio's Component editor uses isolated authoring and site/frame settings use validated writes. Never add a duplicate menu store or falsely treat legacy `site.design.frame` as controlling active component Cards. Avoid unnecessary rewrites, responsive reflow of the print-style website, hosted services or framework dependencies.

## M13 style system — implementation rule

- Styles are **appearance, not structure**. Site design tokens/palette sit in `site.design`; named definitions in `site.design.styles` have `id,name,target,properties`. Nodes can set `styleRef` and optional typed `appearance` overrides. Resolve via `src/style-system.mjs` everywhere, in this order: legacy/site defaults → named style → local overrides. Never flatten styles into duplicated Card trees.
- A styled Card inherits only `background,padding,gap,border`; a styled Item inherits `role,tone,weight`. Keep Card grid geometry, content, links, asset bindings and semantic roles outside style definitions. Do not allow arbitrary CSS or unvalidated properties/variables. `site.design.tokens` currently includes font family, corner radius and outline opacity; the palette remains grayscale.
- Work and Journal opt in with matching `index-root` Card and `eyebrow-label` Item styles. Do not silently migrate Home or existing legacy fields. Studio includes a dedicated Styles library and per-object Inherit/reset controls; its edits must validate before writing JSON. `src/public.css` respects the shared CSS tokens.
- M13 feature code and targeted render checks are committed; all Node/browser/build/ZIP/visual acceptance remains due at the end of V2.

## M14 record compositions — implementation rule

- Project/Post records remain typed data in their Collections. Optional `record.composition` is one uniquely owned root Card; it requires an explicit `record.template` pointing to a one-main-slot Template in the **same Collection**. `collection.compositionTemplate` selects the slot layout for new records and explicit conversions. The existing `defaultTemplate` and `formatTemplates` stay **legacy detail templates** for non-composed records; never replace their layout without opting in.
- `templateFor()` honours explicit record template selection before collection format/default. `renderPagePreview()` and the static `collectPages()` path call the **same** M12 `assemblePage()` for records and resolve `{{...}}` bindings using the owning record. Never duplicate a template tree into a public record except as an explicitly opted-in initial root composition.
- In Studio, a record with a composition has **Design** (isolated editable root), **Preview** (assembled page), **Fields** (typed context) and **JSON**. Existing legacy records retain their original Fields/Preview experience. The root Card is protected and structure edits must be validated, undoable and scoped to the correct record. Duplicating records regenerates composition node IDs.
- `collection.detailPages === false` or `record.detailPage === false` suppresses the public detail route; query/index Cards still render but cannot link to suppressed routes. Defaults remain enabled for backward compatibility, and the Draft status still excludes publication.
- M14's first example is draft post `post-four`, not published. Keep all current live Project/Post legacy detail pages intact until explicit authoring changes or final visual review.

## M15 typed contextual asset queries — implementation rules

- New gallery Cards use the existing authored Card geometry with `source.kind:"assets"`, never a parallel gallery node or asset-ID array on records. The pure `src/asset-query.mjs` evaluator returns deterministic bounded matches from canonical `assets[]` metadata. Allowed fields: `projectCode` equals `asset.properties.projectCode`; `tags` contains one case-insensitive tag; `name` equals/contains. Predicates combine with **AND**. Empty bindings fail closed.
- Record-context values use safe one-field bindings such as `{{projectCode}}`, without arbitrary object paths, code execution, path-based selectors or regex. Query result visuals use the **shared Card/Image renderer** with normal alt/caption handling; NEVER copy or embed media files, or invent relational tables. The Asset Library retains metadata edit controls.
- In Studio the Asset gallery appears in the Add-object picker and has validated source/editor fields, filters, caption, order and count. Newly added filters and existing filters are reversible using the Card's undo history. Preserve legacy record collection query Cards.
- **2026-10-16 user decision:** Existing site content is demo material. **Legacy Pages/Records may be migrated freely during V2 development** when that makes the architecture cleaner; preserve important route/data references and leave `main` untouched. No need to avoid conversions merely to maintain old demo geometry. Balkan House is the first Project converted to a record root with a contextual gallery; Soft Modules was already a draft composition example.
- M15 code has targeted model/renderer checks and committed regression tests, but full local Node/browser/build/ZIP/visual verification remains due at final V2 acceptance.

## GitHub and publishing — user decision 2026-10-15
- **GitHub is source control and the CURRENT website publishing host**, not a testing service or separate staging environment. `main` publishes to GitHub Pages using **one minimal Pages workflow**; no CI test pipelines or ZIP artifact uploads. **Do not require GitHub to run local tests, preview or build.**
- Search indexing is an explicit **site-wide JSON switch** (`site.publishing.indexing`, edited in Studio Overview). The TA placeholder site currently sets it **false**; public HTML emits `noindex, nofollow`, with crawlable `robots.txt` (so bots can discover noindex) and no sitemap. When true, HTML emits `index, follow`; a sitemap is written only with a configured custom-domain `TA_PUBLIC_ORIGIN`. Never impose content approval gates on builds or ZIPs. Neither mode makes the website private; the same setting applies to Pages, local `dist/` and local ZIP. It reaches the current Pages site only after merging/pushing to `main`.
- Authoring, builds and previews work without external hosting or GitHub. Running `npm run preview` locally doesn't need internet; remote Google Fonts may fall back to installed/system monospace when offline. Do not assume double-clicking `dist/index.html` works because site links are root-relative.
- **V1** [PR #23](https://github.com/teodor-andonov/ta-website-builder-261012/pull/23) was squash-merged at `7d5b44556c5bd237b9b8a06bec2322f842b13a00`; keep the V1 branch. **V2** uses one rolling branch `feature/v2-unified-studio`, [PR #24](https://github.com/teodor-andonov/ta-website-builder-261012/pull/24), across M12–M17, with **one final squash** on completion. No intermediate merge or branch deletion.
- User defers real portfolio material, contact booking, Hostinger/domain move and manual QA until **after V2**. Do not fabricate these, but also do not block software development or normal Pages publishing on them. GitHub Pages currently remains the publishing destination.
- **Automations stay paused**. Work only when asked. No screenshots unless the user explicitly reauthorises them.
